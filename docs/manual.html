Manual de EventFlow

Una API de pedidos en Go. Guarda cada pedido en PostgreSQL y publica el evento order.created en RabbitMQ. Un worker lo procesa en segundo plano: confirma el pedido y envía un email simulado, con reintentos y cola de mensajes muertos.

POST /orders→PostgreSQL→order.created→worker→CONFIRMED

Puertos: 3200 API · 3201 worker · 5432 PostgreSQL · 5672 RabbitMQ · 15672 consola de RabbitMQ.

Windows sin permisos de administrador: Go se puede instalar desde el .zip de go.dev. Descomprímelo, por ejemplo en C:\Users\<usuario>\tools\go, y agrega ...\go\bin al PATH de tu usuario. Docker Desktop sí suele requerir permisos de administrador.

Levantar el sistema

git clone <url-del-repositorio> eventflow
cd eventflow
docker compose up -d --build

docker compose ps                 # postgres y rabbitmq "healthy"; api y worker "running"
curl -s localhost:3200/ready      # {"database":"up","status":"up"}

La API crea las tablas sola al arrancar (migraciones). Para detener: docker compose down; con -v también borra la base de datos.

Guía 2

Uso

Crear un pedido

curl -s -i -X POST localhost:3200/orders \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: pedido-001' \
  -d '{"customer_id":"customer-42","items":[{"sku":"SKU-1","quantity":2,"unit_price_cents":1500}]}'

# HTTP/1.1 201 Created
# {"id":"4f1c…","status":"PENDING","total_cents":3000,…}

Los precios van en centavos: 1500 = 15,00. El pedido nace PENDING y el worker lo pasa a CONFIRMED en segundo plano.

En PowerShell:

$body = '{"customer_id":"customer-42","items":[{"sku":"SKU-1","quantity":2,"unit_price_cents":1500}]}'
Invoke-RestMethod -Method Post -Uri http://localhost:3200/orders -ContentType "application/json" `
  -Headers @{ "Idempotency-Key" = "pedido-001" } -Body $body

Reintentar sin duplicar

Si el cliente no recibe respuesta, puede repetir la petición con la misma Idempotency-Key. La primera vez responde 201; las siguientes, 200 con el mismo pedido y sin crear otro. Sin la cabecera, cada POST crea un pedido nuevo.

Ver qué está pasando

docker compose logs -f api worker
docker compose logs api worker | grep <request_id>   # sigue un pedido de punta a punta
curl -s localhost:3201/metrics                        # reintentos, mensajes en DLQ, duplicados…

El request_id del POST viaja dentro del evento como correlation_id, así que un solo grep muestra el pedido en la API y en el worker. La consola de RabbitMQ está en http://localhost:15672 (usuario y contraseña guest, solo en local).

Guía 4

Arquitectura

Componentes

La API y el worker salen del mismo código y la misma imagen Docker, pero corren como dos procesos para que un email lento no afecte las respuestas HTTP.

flowchart LR
    C([Cliente HTTP]) -->|"POST /orders"| API["api :3200"]
    API -->|"1. guarda el pedido"| PG[("PostgreSQL")]
    API -->|"2. publica order.created"| MQ{{"RabbitMQ"}}
    MQ --> W1["worker: order-processor<br/>PENDING a CONFIRMED"]
    MQ --> W2["worker: notifier<br/>email simulado"]
    W1 --> PG
    W2 --> PG

Capas (como en la semilla)

El dominio no importa nada externo; la infraestructura implementa sus interfaces.

flowchart TB
    P["presentation<br/>handler HTTP · consumer de mensajes"] --> A["application<br/>CreateOrder · GetOrder · ConfirmOrder"]
    A --> D["domain<br/>Order, reglas, OrderRepository, EventPublisher"]
    I["infrastructure<br/>PostgreSQL · RabbitMQ"] -. implementa .-> D

Crear un pedido

sequenceDiagram
    actor C as Cliente
    participant UC as CreateOrder
    participant DB as PostgreSQL
    participant MQ as RabbitMQ
    C->>UC: POST /orders + Idempotency-Key
    UC->>UC: NewOrder() valida las reglas
    UC->>DB: INSERT ... ON CONFLICT (idempotency_key) DO NOTHING
    alt la clave ya existía
        DB-->>UC: 0 filas, se lee el pedido original
        UC-->>C: 200 con el mismo pedido
    else pedido nuevo
        UC->>MQ: publica order.created y espera confirmación
        UC-->>C: 201 PENDING
    end

Reintentos y cola de mensajes muertos

flowchart LR
    M[Mensaje] --> T{"¿Funcionó?"}
    T -->|sí| ACK["ACK: listo"]
    T -->|"error transitorio"| R{"¿Quedan intentos?"}
    R -->|"sí: espera 0,5 s, 1 s, 2 s"| T
    R -->|no| DLQ[".dlq para investigar"]
    T -->|"error permanente"| DLQ
    T -->|"apagado durante la espera"| Q["vuelve a la cola"]

Base de datos

erDiagram
    orders ||--|{ order_items : contiene
    orders {
        uuid id PK
        text customer_id
        text status "PENDING o CONFIRMED"
        bigint total_cents
        text idempotency_key UK
        timestamptz created_at
    }
    order_items {
        uuid order_id PK
        int position PK
        text sku
        int quantity
        bigint unit_price_cents
    }
    notifications {
        uuid id PK
        uuid event_id UK
        uuid order_id
        timestamptz sent_at
    }
